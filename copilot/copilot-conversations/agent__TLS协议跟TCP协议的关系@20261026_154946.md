**ai**: 我读了 [[TLS]]（你目前记的是记录层/握手层的头部结构）。在此基础上回答两者的关系——结论先说：**TCP 和 TLS 不是并列关系，TLS 是跑在 TCP 之上的“安全子层”**。

## 1. 分层位置

```
+---------------------------+
|  HTTP / SMTP / IMAP / ... |   应用层
+---------------------------+
|  TLS（握手层 + 记录层）      |   ← 夹在应用层与传输层之间
+---------------------------+
|  TCP                      |   传输层 L4：可靠有序字节流
+---------------------------+
|  IP                       |   网络层
+---------------------------+
```

- **TCP** 负责“送到、按序、不丢、不重、有流控/拥塞控制”，但内容是**明文**。
- **TLS** 负责“机密性、完整性、对端认证”，但它**不负责寻址、端口、重传、排序**——这些全部继续由 TCP 提供。

所以它们的分工是「TCP 提供管道，TLS 把管道里的内容加密封装」，TLS 不替代 TCP。

## 2. 一个容易踩的命名陷阱

TLS 全称 **Transport Layer Security**，但它在 OSI 里并不属于第 4 层（传输层），通常被归到第 5/6 层（会话/表示层），在 TCP/IP 四层模型里算“应用层的安全子层”。你笔记 frontmatter 的标签 `网络协议/传输层` 严格说是有点偏差的——这点后面可以改。

## 3. 封装关系：TLS 记录 ≠ TCP 段

这正是你笔记里那 5 字节记录头的意义：它就在 TCP 头部之后的载荷位置。

```
[ IP 头 ][ TCP 头 ][ TLS 记录头 5B ][ TLS 载荷（加密）... ][ 下一个 TLS 记录 ... ]
                          ↑
                    你笔记第 21-27 行描述的字段
```

边界关系有两点要记清：

| 现象 | 原因 |
|---|---|
| 一条 TLS 记录被拆进多个 TCP 段 | TLS 记录最大 2^14 (16384) 字节，远大于 MSS，TCP 会按 MSS 切分 |
| 一个 TCP 段里装多条 TLS 记录 | Nagle / 发送缓冲合并，或小记录（如 alert）被合包 |
| 应用层 write 一次 ≠ 一条记录 ≠ 一个 TCP 段 | 三层各有各的分片逻辑，不能互相推导 |

握手消息是“记录层负载的一种”：内容类型 `22 (0x16)` 的记录里，可以塞一条或多条握手消息，每条再带 4 字节握手头（你笔记第 30-37 行）。这是**TLS 内部的两层嵌套**，跟 TCP 是第三层嵌套，四层头套在一起。

## 4. 时序关系：先 TCP 三次握手，再 TLS 握手

```
客户端                 服务端
  |---- SYN ----------->|
  |<--- SYN+ACK --------|   TCP 三次握手（1 RTT）
  |---- ACK ----------->|
  |---- ClientHello --->|   TLS 握手
  |<--- ServerHello ----|
  |<--- Certificate ...|
  |---- Finished ------>|   TLS 1.3：总共 1 RTT
  |==== 加密应用数据 ====>|   TLS 1.2：2 RTT（会话复用可降到 1 RTT）
```

- 首字节延迟大致是 `TCP 1 RTT + TLS 1.3 的 1 RTT = 2 RTT`（TLS 1.2 则是 3 RTT）。这也是 TLS 1.3 把握手压到 1-RTT、支持 0-RTT 复用的直接动机。
- TLS 1.3 的 0-RTT 复用在**第一个 flight** 里就带应用数据，但代价是重放风险。

## 5. TLS 对 TCP 的“依赖”体现在哪

这条最能说明二者关系：

- TLS 自己**没有重传、没有序号、没有拥塞控制**。它假设下层是“可靠有序的字节流”，丢包重传全交给 TCP。所以 TLS 记录里没有序列号字段（DTLS 才加）。
- 正因如此，**TLS 不能直接跑在 UDP 上**，否则要有额外改造：
  - **DTLS**：给记录加显式序号 + 重传定时器，模拟可靠性；
  - **QUIC**：把 TLS 1.3 握手消息装进 QUIC 的 CRYPTO 帧，跑在 UDP 上——TLS 只负责派生密钥，可靠性/多路复用由 QUIC 自己实现。这是“拆开 TLS 与 TCP 绑定”的现代方案。
- **关闭语义也不一样**：TCP 的 FIN/RST 不带认证，攻击者可截断连接伪造结束（truncation attack），所以 TLS 有 `close_notify` alert；TLS 1.3 里应用数据读完没收到 close_notify 应报“意外结束”。

## 6. 安全边界：TLS 保护不到 TCP 头

| TCP 头字段 | 是否被 TLS 保护 |
|---|---|
| 源/目的 IP、端口 | ❌ 明文，中间人可见（所以能按 SNI/端口做封锁、做流量分析） |
| 序号、ACK、窗口 | ❌ 明文 |
| 载荷（TLS 记录内容） | ✅ 加密 + 完整性校验 |
| 握手里的证书、SNI | TLS 1.3 中证书已加密；SNI 默认仍明文（需 ECH 才隐藏） |

另外 TLS 与端口没有绑定关系：443 只是约定，TLS 可跑在任意 TCP 端口上；反过来 443 上也不一定是 TLS。

## 7. 一表总结

| 维度 | TCP | TLS |
|---|---|---|
| 层次 | 传输层 L4 | TCP 之上的安全子层（应用层与传输层之间） |
| 核心职责 | 可靠、有序字节流、流控、拥塞控制、连接管理 | 机密性、完整性、对端身份认证 |
| 数据单元 | 段（segment） | 记录（record） |
| 是否重传 | 是 | 否，依赖 TCP |
| 有无端口 | 有 | 无（复用 TCP 端口） |
| 头部 | 20+ 字节，全程明文 | 记录头 5 字节；握手后载荷加密 |
| 结束方式 | FIN/RST | close_notify alert |
| 典型组合 | HTTP/FTP/SSH | HTTPS(443)、SMTPS、IMAPS、DoT |

一句话记忆：**TCP 是可靠的信道，TLS 是在这条信道上先协商密钥、再把字节流加上密的外壳；TLS 的所有“可靠”假设都由 TCP 兑现，TLS 只兑现“安全”。**
