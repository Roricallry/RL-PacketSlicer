## TLS 是独立于端口的，443 只是「约定俗成」

TLS 本身运行在 TCP 之上，并不绑定端口。端口是应用层/IANA 的约定：

| 端口 | 场景 |
|---|---|
| **443** | HTTPS（HTTP over TLS），最典型 |
| 8443 | 备用 HTTPS，Tomcat/后台管理台常用 |
| 993 / 995 | IMAPS / POP3S |
| 465 / 587 | SMTPS / 提交 |
| 636 | LDAPS |
| 853 | DNS over TLS（DoT） |
| 990 | FTPS |
| 5061 | SIP over TLS |
| 8883 | MQTT over TLS |

## 更关键的一点：不是「所有 TLS 数据包都走 443」，而且也要看你说的是哪一层

1. **抓包层面（Wireshark 视角）**：TLS 记录层头部里的 `Content Type` 字段（22 握手 0x16、20 改变密码规范 0x14、21 警报 0x15、23 应用数据 0x17）、`0x0303` 这样的 Record Version，才是识别 TLS 流量的真正依据。很多分析规则都是「看 TCP 载荷前几个字节」，而不是看端口 443。

2. **端口 443 ≠ 一定是 TLS**：443 也可以跑其他静态加密协议。反过来，TLS 也常被放在非标准端口上，来规避基于端口检测的防火墙或策略（比如 443 上的 gRPC、443 上的 QUIC，即 HTTP/3 的 UDP 443）。

3. **443 上也有非 TLS 的 TLS 变体**：QUIC（HTTP/3）基于 UDP 443，它使用的也不是「TLS 记录层」（而是 TLS 1.3 的握手，被直接嵌入 QUIC 包），所以从抓包角度看，它不是「TLS 记录」包。

## 和你的笔记 [[repository/TLS]] 的关系

笔记里讲的是**记录层头部与握手消息头部**，这部分恰恰说明：协议识别应该基于头部字段（Content Type、Handshake Type），而不是端口。可以补一句：

## 规范依据

RFC 8446 §5.2 中 `TLSCiphertext` 结构的定义：

```text
struct {
    ContentType opaque_type = application_data; /* 23 */
    ProtocolVersion legacy_record_version = 0x0303; /* TLS v1.2 */
    uint16 length;
    opaque encrypted_record[TLSCiphertext.length];
} TLSCiphertext;
```

`opaque_type` 的规范说明（§5.2）写明：

> The outer opaque_type field of a TLSCiphertext record is **always set to the value 23 (application_data)** for outward compatibility with middleboxes accustomed to parsing previous versions of TLS. **The actual content type of the record is found in TLSInnerPlaintext.type after decryption.**

## 结构对比

```text
TLS 1.3 加密记录（线上可见）:
+--------+----------+--------+---------------------------------------------+
| 0x17   | 0x0303   | length | encrypted_record                            |
| 明文   | 明文     | 明文   |  = AEAD( content + real_type + zeros[] )    |
+--------+----------+--------+---------------------------------------------+
                                       ^^^^^^^^^ ^^^^^^^^^ 都看不到
真实类型（握手=0x16 / 警报=0x15 / 应用数据=0x17）在密文里
```

## 三个要点

1. **只有加密记录才恒为 0x17**。握手阶段早期的 `ClientHello`、`ServerHello` 记录仍是未加密的 `TLSPlaintext`，此时外层 `type` 是真实的 `0x16`（握手），版本为 `0x0301` 或 `0x0303`。`ChangeCipherSpec` 兼容记录也是明文 `0x14`。

2. **目的是中间盒兼容（ossification）**。有些老防火墙和中间盒会检查记录类型，只允许握手和 `application_data`；把所有加密记录统一标成 `0x17`，中间盒就不会因为看到陌生的握手记录而拦截。

3. **真实类型没有丢失，只是被加密了**。解密后，`TLSInnerPlaintext.type` 给出真实值。接收方从密文末尾往前扫描第一个非零字节，以此定位 `type`；它后面的零字节都是填充。

因此，从抓包角度看，一条 TLS 1.3 连接在 `ServerHello` 之后，就全都是一串“`application_data`、`0x0303`、不同长度”的记录，分不清哪些是真正的握手收尾、哪些是警报、哪些是应用数据。

> [!note] 校验路径
> 这也解释了为什么只看端口或记录类型无法判断 1.3——必须从 `ServerHello` 中的 `supported_versions = 0x0304` 扩展来确认版本协商。

## “内层长度”的准确含义

那句话里的“内层长度拆分”，是相对**外层 `TLSCiphertext.length`** 说的。外层 length 是密文记录的**总长**，其中包含如下几部分：

$$
L_{\text{outer}} = \lvert content \rvert + 1 + \lvert zeros \rvert + 16
$$

（1 = `type` 字节，16 = AES-GCM 的 AEAD tag；ChaCha20-Poly1305 也是 16 字节。）

“拆分”指的是：**在不知道密钥时，无法把 $L_{\text{outer}}$ 分成“真实内容、类型字节、填充、AEAD tag”这四段**。所以你说的“排除 padding 后的实际长度”，确实混在其中；但问题比这更根本。

## ⚠️ 需要纠正的概念

**“内层长度”并不是某个被加密的字段。** TLS 1.3 里 `TLSInnerPlaintext` 的结构是：

```text
opaque content[TLSPlaintext.length];
ContentType type;
uint8 zeros[length_of_padding];
```

这里**根本没有长度字段**。接收方解密后，按“从尾部往前扫描第一个非零字节 = `type`，其前面的都是 content，后面的都是 padding”这条规则来切分。所以：

- **线上**：只有一段可读长度，即外层明文 `length` = 密文总长
- **解密后**：没有长度字段，边界由扫描规则推导出来
- **交给上层时**：才构造出 `TLSPlaintext.length = |content|`，但这个字段**只在实现内部使用，不上线**

因此准确地说：*无法拆分*，而不是*有个“内层长度”被加密了*。你说的“排除 padding 后的实际长度”是**接收方解密后内部得到的那个数**，不是协议传输的内容。

即使配置了密钥（`SSLKEYLOGFILE`），Wireshark 计算 `|content|` 也依赖“算法有密钥、能解密扫描”这个前提；只知道套件时，最多能以 16 字节（tag）为粒度做估算，而且填充会让这个估算不准确。

**ai**: **是的，AEAD tag 长度由具体 AEAD 模式决定；更准确地说，它并不完全由“加密算法”决定，而是由加密算法和认证模式的组合决定。**

## TLS 1.3 定义的套件

RFC 8446 附录 B.4 只定义了这 5 个套件，它们的 tag 长度都是固定的：

| 套件 | AEAD | tag 长度 |
|---|---|---|
| `TLS_AES_128_GCM_SHA256` (0x1301) | AES-128-GCM | **16 字节** |
| `TLS_AES_256_GCM_SHA384` (0x1302) | AES-256-GCM | **16 字节** |
| `TLS_CHACHA20_POLY1305_SHA256` (0x1303) | ChaCha20-Poly1305 | **16 字节** |
| `TLS_AES_128_CCM_SHA256` (0x1304) | AES-128-CCM | **16 字节** |
| `TLS_AES_128_CCM_8_SHA256` (0x1305) | AES-128-CCM-8 | **8 字节** |

## 关键点

1. **规范中的说法是“expansion”**。RFC 8446 §5.2 定义 `TLSCiphertext.length` 时写的是“plus **any expansion added by the AEAD algorithm**”，并规定：

   > An AEAD algorithm used in TLS 1.3 MUST NOT produce an expansion greater than **255 octets**.

   也就是说，规范只设置了上限，具体值由每个 AEAD 算法自身定义（RFC 5116 中的 `n_t`）。

2. **AES / ChaCha20 决定的是分组密码，tag 由 AEAD 模式决定**。
   - 同样使用 AES，如果换成 GCM 模式，tag 为 16 字节；如果换成 CCM 模式，tag 可以配置为 8 字节或 16 字节，例如上面第 5 个套件就是 8 字节。
   - Poly1305 是 ChaCha20-Poly1305 组合中的认证部分，固定为 16 字节。

3. **TLS 1.2 里 tag 长度的不确定性更大**：AEAD 套件（GCM/CCM）同样会产生 tag，但 CBC 套件用的是 HMAC，而 HMAC 长度取决于哈希（SHA-1 为 20 字节、SHA-256 为 32 字节、SHA-384 为 48 字节）。所以在 1.2 里，这个参数更加不确定。

4. **TLS 1.3 有从 AEAD 输出中直接读取 tag 的便利**：由于全部使用 AEAD，如果已知套件，$t$ 就是确定值；但如果**不知道协商出的套件**（ServerHello 已加密且没有密钥），就只能假设 $t$ 为常见值 16 字节，这也是无密钥分析时可能出错的地方。
