## TLS 是独立于端口的，443 只是「约定俗成」

TLS 本身运行在 TCP 之上，并不绑定端口。端口是应用层/IANA 的约定：

| 端口 | 场景 |
|---|---|
| **443** | HTTPS（HTTP over TLS），最典型 |
| 8443 | 备用 HTTPS，Tomcat/后台管理台常用 |
| 993 / 995 | IMAPS / POP3S |
| 465 / 587 | SMTPS / 提交 |
| 636 | LDAPS |
| 853 | DNS over TLS（DoT） |
| 990 | FTPS |
| 5061 | SIP over TLS |
| 8883 | MQTT over TLS |

## 更关键的一点：不是「所有 TLS 数据包都走 443」，而且也要看你说的是哪一层

1. **抓包层面（Wireshark 视角）**：TLS 记录层头部里的 `Content Type` 字段（22 握手 0x16、20 改变密码规范 0x14、21 警报 0x15、23 应用数据 0x17）、`0x0303` 这样的 Record Version，才是识别 TLS 流量的真正依据。很多分析规则都是「看 TCP 载荷前几个字节」，而不是看端口 443。

2. **端口 443 ≠ 一定是 TLS**：443 也可以跑其他静态加密协议。反过来，TLS 也常被放在非标准端口上，来规避基于端口检测的防火墙或策略（比如 443 上的 gRPC、443 上的 QUIC，即 HTTP/3 的 UDP 443）。

3. **443 上也有非 TLS 的 TLS 变体**：QUIC（HTTP/3）基于 UDP 443，它使用的也不是「TLS 记录层」（而是 TLS 1.3 的握手，被直接嵌入 QUIC 包），所以从抓包角度看，它不是「TLS 记录」包。

## 和你的笔记 [[repository/TLS]] 的关系

笔记里讲的是**记录层头部与握手消息头部**，这部分恰恰说明：协议识别应该基于头部字段（Content Type、Handshake Type），而不是端口。可以补一句：

**ai**: 我已在 [[repository/TLS]] 新增第 4 节「空长度记录与填充：流量分析对抗」。你的判断**大部分正确，但有一处关键偏差**：

## ✅ 说对的部分

1. **TLS 1.2 和 1.3 都允许零长度应用数据记录**，而且规范原文给出的理由就是流量分析对抗（RFC 5246 §6.2.1、RFC 8446 §5.1/§5.4）。注意：这只是 `application_data` 类型允许；handshake/alert 的零长度记录是 **MUST NOT**。
2. **TLS 1.2 的记录头部明文**，攻击者能直接看到 `type=0x17` 和 `length=0`。
3. **TLS 1.3 增加了填充**：`TLSInnerPlaintext = content + type + zeros[...]`，填充与真实类型一起参与 AEAD 加密。

## ⚠️ 需要修正的部分

**「1.2 里攻击者能轻易看破哪些是 0 数据包，因为记录是明文」这一因果链不完全成立。**

准确来说，TLS 1.2 里攻击者能直接看出空记录，是因为记录头明文，**这和“0 数据包”本身无关**；即使是有数据的记录，攻击者也能看出类型和长度。而且，1.2 的内容长度同样无法被直接看穿，只能靠“总算长减去 MAC/IV/填充”来推算，CBC 模式的 padding 还会让这个估算模糊化。

RFC 5246 §6 原话是：“**type and length of a record are not protected by encryption**”，泄漏的是**记录边界、类型、总长度**这三样。

**更准确的 1.2→1.3 演进表述是：** 1.3 把**类型**也藏进密文（外层 ContentType 恒为 `0x17`），并给了**应用层可选的任意长度加密填充**。因此攻击者知道“有一条记录、多长”，但不知道“里面是什么类型、真实内容多长”。

## ❗ 还要强调的

1.3 的填充**并不解决**流量分析：RFC 8446 附录 E.3 明说长度和时序仍可观测，填充是应用**可选**的，不是自动定长。真正抗流量分析要靠应用层定长填充或恒定速率发送。
